\hypertarget{index_MainIntroduction}{}\doxysection{\texorpdfstring{Introduction}{Introduction}}\label{index_MainIntroduction}
The objective is to provide a set of tools, simple, light, fast, well architectured that allows to manage unstructured contents. No sql access is required. Access is made thru relative positionning, or direct content access either through defined keys or even in the unstructured content itself.

Nowadays a maximum of content, documents, mails, images, are
\begin{DoxyItemize}
\item stored remotely on servers and accessed through the net,
\item then loaded in local memory, and stay resident most of the time.
\end{DoxyItemize}

Even if memory tends to be huger and huger, we face strong limitations in terms of resources either network resources and local resources.

The proposed tools are designed to manage contents with the following main advantages \+:
\begin{DoxyItemize}
\item they can be embedded directly in applications \+: these tools may perfectly work on a mobile phone, as well as a linux or windows server.
\item so that they can run locally and store locally documents in a private
\item usage of these documents does not consume network bandwidth and can even be done off-\/line
\item the same application may run on various operating system without change
\item they are "{}\+QT compatible"{} even if they do not require QT to work fine (no QT libraries are required)
\item they are very few resources consumming
\item they are quick because written in C++
\item they are "{}manageable"{}, with a set of tools to analyse, maintain, migrate and recover
\end{DoxyItemize}\hypertarget{index_MainWhat}{}\doxysection{\texorpdfstring{What content management are we talking about ?}{What content management are we talking about ?}}\label{index_MainWhat}
The idea is to store locally the content we do need the most, in order to skip the gap of network, and this, without degrading local performance for applications that finally may "{}starve"{} from lack of local resources.

Additionally, it is safer because we all know that transitting by the net is not very safe, and the network encoding itself consumes as well pretty much resources.

Purpose of this tool set is to provide two main functionalities that will be exposed below.\hypertarget{index_MainContent}{}\doxysubsection{\texorpdfstring{Huge contents management with ZRandom\+File}{Huge contents management with ZRandomFile}}\label{index_MainContent}
We intend to manage huge contents, with a varying size, with an optimized space management.

Access is done per relative position of each content block (record).

But it offers at this stage, full search capabilities using its "{}field"{} definition. What is proposed here is not only "{}full text"{} search, but a search on a byte sequence in part of a file (collection of records), or in the total file content. When can then, for example, search for set of pixel values in various image documents, or a even a machine code segment, if content is executable.

For performance purposes, \doxylink{classzbs_1_1_z_random_file}{ZRandom\+File} is composed of 2 physical files that may strictly stay aligned \+:
\begin{DoxyItemize}
\item Content file This is the main file that will contain user data. This is the file that is named by used to handle a \doxylink{classzbs_1_1_z_random_file}{ZRandom\+File}. The name of this file is left to user\textquotesingle{}s choice, despite some restrictions(see below). This name will actually be the name of the \doxylink{classzbs_1_1_z_random_file}{ZRandom\+File} itself.
\item Header file This file contains infradata that is mandatory to the \doxylink{classzbs_1_1_z_random_file}{ZRandom\+File} behavior. The name of this file is deduced from the content file and is stored in the same path that content file.
\end{DoxyItemize}

\begin{DoxyNote}{Note}
\doxylink{classzbs_1_1_z_random_file}{ZRandom\+File} users do not have to care about this duality, excepted when ZRandom\+Files are backuped or moved. Header file name is transparently deduced from the content file name (uri\+String). In a normal usage case, user does not see header file. He only addresses the main \doxylink{classzbs_1_1_z_random_file}{ZRandom\+File} content file, the one he named.
\end{DoxyNote}
\begin{DoxyWarning}{Warning}
This implies that header file is absolutely necessary for a \doxylink{classzbs_1_1_z_random_file}{ZRandom\+File} to be recognized and to be read. Users should never ever modify directly, or even delete, such files, nor move them without moving the main ZRF content file. In such cases, damages could stay non recoverable. However, there is an utility routine to rebuild a header file in case of damaged header file \doxysectlink{group___z_r_f_utilities_ZRFUtilHRebuild}{ZRF header rebuild}{2}
\end{DoxyWarning}
